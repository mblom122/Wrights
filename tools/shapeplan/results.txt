## 1. What one hover can actually finish

A full 19-cell hover and the next full hover cannot sit on adjacent blocks.
Centers one step apart, or one diagonal step apart, share cells. The closest
integer steps that share nothing are already farther than the 1.5-block arrive
radius, so the wright spends a fly tick between two full hovers.

## 2. Easy grids versus the lattice

A perfect fill would be one residue class modulo 19, 19 blocks every hover.
Every linear form collides inside the sphere, and every index-19 lattice is one of
those forms (19 is prime). So a disjoint 19-tiling by translations does not exist.
The lattice below is the best covering that still fits in the sphere:
  modulus 11, interior hover 11 blocks, cap use 57.9%.

Checked on a 11^3 cube (1331 cells):
  lattice hovers 192 (expect 121)  cells 1331

First-fit from the corner of a 19^3 cube (claim the sphere and move on, no lattice):
  hovers 1729  leftover 0  cap use 20.9%
  lattice on that same 19^3:
  hovers 829  cells 6859  cap use 43.5%

Exact-cover search for a perfect 19-tiling on the smallest wrap-free torus (19x3x3):
  proved there is no perfect tiling (58595 nodes) in 26.61 ms

The live estimate usefulCrewFor divides each side by 3. That pretends a hover
covers a 3x3x3. It does not: the corners are outside the sphere, and a 3-step
grid leaves a hole on every (2,2,2) mod 3. Measured leftover is below.

## 6. Server tick cost, now versus a streamed hover

Probe the live code uses when it has no stored hover (FLY_NEAR_RADIUS = 8):
  cells visited per wright per new hover: 4913 (17^3). Near cluster is 729 (9^3).
  measured arithmetic only: 17478 ns per probe. World checks are not in that number.
  streamed next hover, 10 wrights: 2 ns (sink 0).

If each visited cell also does a block lookup + permission + shape test, at an assumed
200 ns each (not measured — a floor for 'maybe cheap' and a ceiling for 'getBlockState plus rules'):
  one wright: 0.98 ms of lookups
   1 jobs × 10 wrights:    9.83 ms per server tick   ok
   5 jobs × 10 wrights:   49.13 ms per server tick   heavy
  10 jobs × 10 wrights:   98.26 ms per server tick   OVER a 50 ms tick
  20 jobs × 10 wrights:  196.52 ms per server tick   OVER a 50 ms tick
A streamed plan checks the ≤19 cells it is about to place, not the 4,913-cell cube around the wright.
  20 jobs × 10 × 19 × 200 ns = 0.76 ms per tick.

Up-front plan, if every job planned on the same tick (lattice planMs is in section 4):
  10 players × 2 jobs = 20 plans. Anything under ~1 ms per plan stays inside a tick even as a herd.
  Pair search is already illegal past 192 blocks because one plan can exceed a tick.
